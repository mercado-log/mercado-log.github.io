# Oque é um conteiner?

Um conteiner, dizendo de maneira simplificada, é um pacote de uma aplicação que contem tudo aquilo que ela precisa para rodar, mas com dois grandes detalhes:
+ 1 - Aplicação isolada do hospedeiro
+ 2 - Aplicação montada em um ambiente linux
A primeira vista confuso, mas com isso pode-se resumir que um container nada mais que um "mini sisteema" que serve apenas para subir um processo principal, isto pois ao falar "mini" me refiro que ele não chega nem perto de um sistema operacional como veremos mais adiante, incluindo sua maior diferença com as VM's, oque discutiremos no proximo topico e melhore o entendimento

# VM x Conteiner

Maquinas virtuais (VM's) são virtualizações de sistemas completos que gastam muito recurso das maquinas que as utilizam, isso pois ao criar uma VM você criar um computador logico completo dentro de uma maquina hospedeira, por ser completo ele naturalmente utiliza de mais recursos para fazer essa simulação, enquanto o docker pega somente o preciso para rodar um processo especifico, como no exemplo acima, um servidor de banco de dados, um servidor web, etc.

Os conteiners simulam o necessario e deixa de fora alguns componentes pesados como programas embutidos e até mesmo o propio kernel do sistema, assim tendo que usar um "adaptador" para se comunicar com o kernel hospedeiro, um grande exemplo é o docker para windows que precisa da instalação do WSL2 para que haja a devida comunicação

Além de tudo isso o conteiner se destaca por ser mais leve, gerenciável e portátil, podendo compartilhar algumas imagens, que são instruções txt para o programa ler e pxar tudo que é necessario.

Por outro lado VM´s tambem tem certo nivel de portabilidade e funcionam como uma maquina completa, tecnicamente uso os dois para manter um isolamento e principalmente para montar laboratórios

# Conceitos e Comandos

Alguns dos comandos que mais uso para criar ou gerenciar um container, no docker,  são os seguintes:
	``` docker run ```
	Comando para puxar alguma imagem e possui alguns parametros como 
	 ``` -p para redirecionar portas
	   -d para instalar e não entrar no conteiner
	   -n para especificar a rede que for usar
	   -v para especificar onde os dados irão ficar
	   -e para especificar as variaveis de ambiente
	   -i para permitir a entrada de teclado, usado em conjunto com o -t
	   -t para criar um terminal no container especificado```
Esses são alguns que consigo lembrar de cabeça e uitlizo no dia a dia.



Além do ``` docker run ``` vale a pena também citar o plugin nativo do docker chamado ```docker compose```, se trata de um plugin que permite subir um ou mais conteiners em um arquivo ```.yaml```, isso permite que você gerencie e documente alterações em conteiners, esta é a estrutura de um docker compose:

![docker compose de um conteiner zabbix, zabbix server e grafana](/assets/images/1-docker-compose-ex.png)

É bom ressaltar que ao rodar do comando ```docker compose```em um compose já ativo ele irá puxar suas atualizações disponíveis e caso acrescente algo a mais na imagem ele irá baixar e instalar apenas o conteúdo novo, além de tambem configurar todos os conteiners em uma rede só automaticamente.

# Como diferenciar(ou tentar)

Atualmente venho usando IA para "turbinar" meus estudos da seguinte maneira: penso em diferentes cenarios que vão além da aula/curso proporciona e através dessa duvida perguntei as diferenças visuais de um container para um s.o completo, algo como um cenário em que eu me conecto em uma maquina e preciso descobrir se ela é um container ou não.

Algumas maneiras que achamos são verificações basicas, como o primeiro processo do sistema, o hostname e o kernel utilizado:

![comandos executados dentro e um conteiner](/assets/images/2-diferença.png)

Há alguns padrões, em containers normalmente o nome do host é um hash, o PID 1 é o bash ou algum outro tipo de processo que não se trata do systemd, cron, init ou processos  comuns do sistema como esses.

Vale tambem a dica que caso queira criar um honeypot, é valido alterar todas essas configs default para deixar o mais proximo possivel de um sistema completo.

# Conclusão

A ideia de containers se assemelha bastante a um sistema de certa maneira parecida com os containers da vida real, afinal de contas cada container é isolado por si só, assim como os conteiners, e compartilham do mesmo ambiente, no ponto logico seria o kernel e no fisico os navios. Por fim, cabe resumir containers como um grande avanço que nos ajudou a melhorar a eficacia, segurança e gerenciamento de aplicações e serviços.

Termino esse post citando a frase do meu professor que apresentou essa solução com as seguintes palavras: "Graças a isso eu consigo rodar essa todas essas aplicações em serviços em uma maquina como essa".
